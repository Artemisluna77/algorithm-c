# 文档组织规范

## 按功能查找

长期维护的方案、设计、审查、操作与验收说明放在 `docs/<module>/`，按正文对应的实际功能确定唯一主模块。同一功能的跨页面资料集中存放，其他模块通过链接关联，避免复制多份正文。

英文文件名移除目录已表达的模块前缀，保留用途、阶段、日期和版本。例如 `dashboard-workbench-refactor-validation.md` 可归为 `dashboard-workbench/refactor-validation.md`；这是结构示例，不要求项目创建该模块。

通用运维资料可保留公共分类，代理约定和 ADR 保留专用结构；已有合理的模块内部层级可以沿用。模块较多时维护 `docs/README.md` 索引，只链接实际存在的资料，不为空目录批量创建占位总览。

## 命名与例外

- 新增目录和文档默认使用英文 kebab-case；模块总览使用 `overview.md`。
- 已有中文文件保留原名；文档整理时允许按功能移动并修复必要引用，不借机删减正文或改变历史结论。
- `AGENTS.md`、`CLAUDE.md`、术语文档、`ROADMAP.md`、`PLAN.md` 等项目入口保留既有位置，完整文件名不区分大小写；带业务前缀的计划文档不属于此例外。
- 工具、组件和包的 README、tracker 的 spec/map/编号工单及评论结构、工单执行证据、运行配置、代码读取的资源、技能配置和源数据保留其约定位置。
- 模块说明的 YAML 示例、附件和证据保持配套关系；不按扩展名机械搬迁，不把模板与运行配置混为一谈。

## 维护引用与证据

1. 迁移前检查工作区并记录旧新位置或保留理由，确认目标唯一且不会覆盖已有资料；现有仓库的大范围归档需要明确任务授权。
2. 移动后修正文档自身及所有可维护调用方的相对链接、源码路径、附件、锚点和索引，包括工单、项目入口、脚本与技能说明。
3. 先判定路径所属仓库；外仓同名文档不能替换成本仓的新位置。历史映射表的源位置、历史 URL 和机器报告中的扫描来源分别保留为证据。
4. 生成报告输出目录确有变化时同步调整生成器；保留运行依赖、源数据与有效配置，不为路径元数据重新生成历史验收结论。
5. 核对文件完整性与正文差异，检查本地链接和可维护旧路径。区分新增断链、既有问题与未验证的远程链接，报告实际检查范围。
